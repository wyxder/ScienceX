# ScienceX 面试讲解与问答手册

> 适用场景：AI 全栈 / AI 应用开发 / Agent 工程师岗位面试（校招、社招通用）。
> 与 `docs/路演.md`（评委向 Q1-Q30）、`docs/路演-新增问题.md`（Q31-Q39）、`docs/答辩讲解.md`（现场演示稿）配套使用，本文是**求职面试向**的版本。
> 使用方式：先背第二节的三版稿，再按第四节把简历 7 条过一遍，最后用第五节的 Q&A 做模拟追问；`docs/简历1.md` 是 STAR 素材库，不必逐字背。

## 〇、先记这 5 句（面试记忆锚点）

1. **一句话定位**：ScienceX 是把「选题 → 文献 → 复现 → 实验 → 分析 → 写作 → 投稿 → 协作」串成一个闭环的 AI 科研工作台，本质是**把科研里"搬数据"的活交给 Agent**。
2. **三个技术抓手**：SSE 全链路流式、多智能体并行编排的容错链、可核查的 RAG 页码级溯源。
3. **我做得最重要的一件事**：把"不确定"变成"可见"——模型降级、检索降级、评审回退、数据是演示还是真实，全部在界面上如实标注。
4. **工程上的差异化**：把 AI 质量做成门禁——55 条自动化用例 + 12 条学术质量评测，低于分数线 CI 直接失败。
5. **价值总结**：这个项目最大的价值不是模块多，而是证明了 AI 产品可以**可复现、可追溯、可问责**。

> 记忆技巧：1 是"是什么"，2 是"深在哪"，3 是"价值观"，4 是"工程化"，5 是"升华"。面试卡壳时任意一句都能接回主线。

## 一、面试策略：3 个锚点 + 1 个钩子公式

### 1.1 先想清楚面试官在判断什么

| 面试官的疑问 | 你要给的证据 | 对应素材 |
| :--- | :--- | :--- |
| 这是真的做过，还是拼凑的？ | 能说出**失败路径**和**踩过的坑** | 第六节四个故事 |
| 技术深度够不够？ | 能讲清**数据流/事件流**，能解释**为什么不用 X** | 第三节三个深挖点 |
| 能不能落地？ | 有测试、有 CI、有部署、有边界声明 | 第七节数字口径 |
| 好不好合作？ | 主动区分"我做的/团队做的"，不抢功 | Q66、Q73 |

### 1.2 回答公式：结论 → 机制 → 取舍 → 边界（40 秒一个回合）

- **结论**（10 秒）：先给一句人话结论，不要铺垫背景。
- **机制**（15 秒）：讲数据怎么流、事件怎么发、失败怎么回退。
- **取舍**（10 秒）：讲"我为什么没选另一个方案"——这是区分"用过"和"设计过"的关键。
- **边界**（5 秒）：主动说一句局限，换取信任。

示例（问"RAG 怎么做的"）：
> 结论：我们做的是"每句话都能追到页码"的 RAG，不是追求回答多花哨。
> 机制：解析阶段就保留段落级页码，切片按 1000 字步长、1200 字窗口带 200 字重叠，向量召回 topK=3，Embedding 挂了自动降级词法检索。
> 取舍：没有一上来就上 pgvector 和 Rerank，是因为演示环境要零依赖可复现，Rerank 做成开关并强制校验返回 ID 集合。
> 边界：向量目前存进程内/JSON，生产要换 pgvector，这个我在 TSD 里写清了。

### 1.3 钩子公式：把面试官引到你的深水区

**句式：「这里其实有个坑，我当时…」+ 一句悬念 + 停 1 秒。**

面试官 90% 会顺着追问。五个可复用钩子：

1. "流式输出最怕的不是断线，是**断了之后假装成功**，我们专门写了用例禁止伪造 done。" → 引到 Q11、故事 6.1
2. "五个 Agent 并行，最大的敌人不是模型不行，是**JSON 解析失败**。" → 引到 Q24、故事 6.2
3. "切片看着简单，但 1000 和 1200 这两个数字是有讲究的。" → 引到 Q29
4. "我们的评测里有一条是**必须拒答**，命中率必须等于 1。" → 引到 Q42、Q44
5. "Serverless 上最容易翻车的不是业务代码，是**内存里的 Session**。" → 引到 Q13、Q14

### 1.4 三条禁忌

1. **不要背功能清单**。面试官不关心你有 12 个模块，关心你能讲透 1 个模块。
2. **不要说"全是我一个人做的"**。一旦被追问某个细节答不上，整份简历都会被怀疑。用"我负责的是…，团队另外一位负责…"。
3. **不要主动抛未验证的准确率**。准确率是面试里最容易被击穿的数字，见第七节。

### 1.5 时间分配建议（45 分钟面试）

- 自我介绍 + 项目讲解：12-15 分钟（占三分之一）。
- 技术追问：20 分钟（重点在 Agent / RAG / 工程）。
- 反问与收尾：5 分钟。

**项目只讲 3 个深挖点，其余一句带过。** 讲得广不如讲得深。

## 二、三版项目讲解稿（可直接背）

### 2.1 30 秒版（自我介绍里的一句话项目）

> 我最近主导开发了一个科研 AI 工作台叫 ScienceX，覆盖从选题、读文献、做实验到写作投稿的全流程。技术上是 React + TypeScript 前端、Node/Express 后端，自研了一套支持 8 种模式的 Agent 编排引擎，还有 5 角色并行的 AI 评审团。项目已经上线并有在线 Demo，55 条自动化用例接进了 CI。
>
> 【停顿】其中我做得最深的是**流式链路**和**多智能体的容错**，如果您感兴趣我可以展开讲一块。

要点：**30 秒内必须出现"上线 + 55 条用例 + 一个深挖点"**，其他都是背景。

### 2.2 90 秒版（"介绍一下你这个项目"）

> 好的，我用三句话说清它是什么、为什么做、我做了什么。
>
> **第一，它是什么。** ScienceX 是一个一站式科研 AI 工作台。研究生做科研要在知网、PDF 阅读器、Origin、Word、期刊官网之间来回切换，每换一个环节就要复制粘贴、重建上下文。我们把这八个环节放进同一个工作台，让数据在模块之间自动流转。
>
> **第二，为什么这么做。** 通用大模型是"有脑无手"，缺专业工具；垂直工具是"有手无脑"，缺编排和闭环。所以我们做的是中间那层：**用 Agent 把专业能力串起来**。
>
> **第三，我做了什么。** 我主要负责三块：一是 Agent 编排引擎，支持 General、ReAct、Plan-Execute、CodeAct 等 8 种模式，统一走 SSE 事件流回传思考和工具调用；二是 5 角色并行评审团，用角色对抗降低单一模型的确认偏误；三是 RAG 的可核查链路，回答必须带文档 ID、页码和原文片段。
>
> **结果**：项目已上线，55 条自动化用例 + 12 条 AI 质量评测接进 CI，拿了 2026 西安黑客松 AI 软件赛道第二名，也进了魔搭 AI 黑客松决赛。
>
> 【停顿】您想先听 Agent 编排，还是先听 RAG 的溯源？

要点：**结尾必须给选择题**，把主动权拿回来，同时暴露你的两个强项。

### 2.3 3 分钟版（"详细讲讲这个项目"，带节奏标记）

> **【0:00-0:40 问题】**
> 我先说问题。科研的痛点不是"没有 AI"，是**工具割裂**。一个课题从想法到发表，至少跨 6 个工具，每次切换都在丢上下文。更麻烦的是，科研场景对"编造"是零容忍的——引用错了、页码错了，是学术诚信问题。所以我们从一开始就定了两条产品原则：**全流程闭环**，和**每一句输出可核查**。
>
> **【0:40-1:30 方案】**
> 方案上我们做了一个"对话即工作台"的结构：中间是 Agent 对话中枢，周围是 12 个科研模块。技术上分六层：React 前端 → Vercel/Express 中间件（CORS、Request-Id、限流、HMAC 鉴权）→ 7 个业务路由域 → AI 能力层（灵犀引擎、三层记忆、RAG、MCP）→ 模型网关 → 数据层。三类数据流：同步 REST、流式 SSE、异步任务 + 进度流。
>
> **【1:30-2:30 三个深挖点】**
> 我挑三个点讲。
> 第一，**流式**。7 类 SSE 事件按序推送，前端逐 Token 渲染、支持主动中断；长任务走独立进度通道。我们专门处理了一个坑：流已经开始输出后如果被截断，**绝不能补一个 done 事件**，否则用户会拿到半截答案却以为完成了。
> 第二，**多智能体**。5 个角色各带独立 system prompt、禁止越界评价，并行调用后由主席合议。真正难的不是并行，是**容错**：JSON 解析失败要宽松提取、单角色失败要重试一次、再失败要逐角色确定性回退，保证报告永远能出来。
> 第三，**RAG**。切片时就把页码带上，向量召回失败自动降级词法检索，回答通过 reference 事件带原文片段，检索为空时明确说"无可用片段"，而不是让模型编。
>
> **【2:30-3:00 结果与反思】**
> 结果上，项目上线了，55 条自动化用例全过，12 条 AI 质量评测里 4 条"拒答诚实度"是强制项。反思也很明确：数据层还是 JSON Store，只适合演示；CodeAct 的沙箱是内置执行器，不是真容器；向量是进程内实现。这三件事是我下一步要补的。
>
> 【停顿】如果只让我讲一块，我建议讲**评审团的容错设计**，那块踩坑最多。

要点：**主动说局限**是这场面试的加分项，因为它证明你知道生产级差在哪。

## 三、主线讲解脚本：一条线讲完整个项目

### 3.1 痛点开场（30 秒，讲人话）

> 我观察到一个现象：一个博士生一天的工作，可能有 40% 时间在**搬东西**——把 PDF 里的结论搬到笔记里，把实验数据搬到 Excel 里，把图表搬到 PPT 里。真正"思考"的时间被挤得很碎。
>
> 所以这个项目的目标不是"做一个更聪明的模型"，而是**做一个能替人搬东西的工作台**。这就是为什么我们强调"闭环"，而不是"功能多"。

### 3.2 一句话架构（配合画图或切屏）

```
浏览器 React SPA（逐 Token 渲染 / AbortController 中断）
   ↓ REST + SSE
Express 中间件链：CORS 白名单 → X-Request-Id → 限流 → HMAC 鉴权
   ↓
7 个路由域：chat / literature / documents / research / dreampaper / publish / account
   ↓
AI 能力层：灵犀引擎（8 模式） + 三层记忆 + RAG + MCP + 模型网关
   ↓
数据层：JSON Store（演示级） → 生产目标 PostgreSQL + Redis + pgvector
```

> 架构上我想强调一点：**契约先行**。前后端共享一套 Zod schema，OpenAPI 是从 schema 同源生成的，不是手写文档。这样接口不会漂移，前端也不需要等后端。

### 3.3 三个技术深挖点（按岗位二选一或三选二）

#### 深挖 A：流式链路（适合偏后端/全栈岗）

讲三层：

1. **协议层**：`start → tool → delta → progress → reference → done/error` 七类事件；对话和长任务分两条通道（`/chat/completions` 与 `/tasks/:id/stream`）。
2. **前端层**：Fetch ReadableStream + 手写 SSE 解码器（`frontend/src/api/client.ts` 的 `readSSE`），逐 Token 渲染，AbortController 主动中断；客户端断开后服务端 abort 上游，避免继续烧 token。
3. **失败层**：这里有个反直觉的设计——**流已经输出过 delta 之后失败，不允许重试、不允许伪造 done**。因为重试会让用户看到两段重复内容，伪造 done 会让半截答案看起来像完整答案。

一句话收尾：
> 流式不难，难的是**流式下的失败语义**。我们把"失败"当成一等公民来设计。

#### 深挖 B：多智能体评审（适合 AI 应用/Agent 岗）

讲四步：

1. **角色拆解**：理论、方法、实验、写作、伦理，对应真实审稿人会攻击的五个面；五维 + 主席总分 = 报告里的六维评分。
2. **隔离**：每个角色独立 system prompt，明确"只评本维度、严禁越界"；温度 0.3 降低发散。
3. **并行 + 容错**：`Promise.all` 并行；JSON 宽松提取（去 Markdown 围栏 → 截取大括号 → 逐字段回补）→ 单角色重试一次（并把 max_tokens 从 1600 提到 2600）→ 逐角色示例回退。
4. **合议**：主席 Agent 拿到五份意见，输出 decision、总分、分歧点、P0/P1/P2 修改清单。

一句话收尾：
> 多智能体的价值不是"人多力量大"，是**让不同角色互相反驳**，把单一模型的确认偏误压下去。

#### 深挖 C：可核查 RAG（适合 RAG/算法应用岗）

讲四个数字：

- **1000 / 1200**：步长 1000，窗口 1200，等于 200 字重叠，避免一句话被切断在两个切片里。
- **3 / 12**：最终返回 topK=3，候选池 12，给 Rerank 留重排空间。
- **1 次降级**：Embedding 不可用 → 词法检索（`keyword-fallback`），并把 mode 和 warning 如实返回前端。
- **0 编造**：检索为空直接告知"无可用片段"；页码没有可靠映射时 `page_verified=false`，不假装有。

一句话收尾：
> 我们不承诺消灭幻觉，我们承诺**每一句输出可核查**。这是科研场景的底线。

### 3.4 收尾：结果 + 反思（20 秒）

> 结果上：项目已上线、55 条自动化用例通过、CI 五重卡口（后端测试 → 覆盖率 → AI 质量回归 → 前端类型检查 → Lint → 构建）。
> 反思上：我知道它的天花板在哪——JSON Store 不适合生产、向量检索是进程内实现、CodeAct 不是真沙箱。这三点我没有藏，写在了 README 的边界表里。

## 四、简历 7 条逐条讲法

> 用法：每条准备 30 秒口语稿；【可深挖】是面试官大概率追问的方向；【边界】是必须主动说清、否则会被击穿的地方。

### 4.1 8 大对话模式

**30 秒口语稿**
> 这 8 种模式不是换皮肤，是 8 条独立的推理管线。General 直答；ReAct 走"思考 → 行动 → 观察"循环；Plan-Execute 先产出一份可编辑的计划，再逐步执行；CodeAct 生成代码、进沙箱、读结果；MCP 走工具握手；Skill 调内置技能；Text2SQL 把自然语言转成查科研数据的 SQL；Structured 输出严格 JSON 供下游渲染。
> 工程上它们共用一个入口 `executeAgentStream`，按 `agent_mode` 分发，但共用一套 SSE 事件协议。这样前端只写一套渲染器，加新模式不用改前端。

**可深挖**
- 为什么统一事件协议？→ 前端渲染器复用、可观测性统一、断连中断统一。
- ReAct 具体一轮是什么？→ thought → tool_call → tool_result → 下一轮 thought，最多设轮次上限。
- 越权怎么处理？→ 资源越权统一 404；模型无权限时显式失败关闭，不静默兜底。

**边界**
> CodeAct 目前是内置的确定性执行器（返回预置执行结果），不是真 Python 容器；真实沙箱在路线图上。这句必须主动说，否则被问"怎么隔离的"会答不上。

### 4.2 多 Agent 评审

**30 秒口语稿**
> 投稿前最大的浪费是"被拒了才知道审稿人攻击什么"。所以我们做了 5 个角色 + 1 个主席：理论看推导和假设边界，方法看架构和创新性，实验看数据集、消融和显著性，写作看结构和符号一致性，伦理看数据授权和学术诚信。
> 每个角色只评自己的维度，五份意见并行生成后，主席做 Meta-Review，输出最终决策、六维评分和 P0/P1/P2 修改清单。

**可深挖**
- 角色怎么定？→ 对标真实审稿意见的维度切分，不是拍脑袋；五个维度覆盖"能不能成立、新不新、证没证、写没写清、合不合规"。
- 怎么防串味？→ system prompt 里写死边界 + 每个角色独立的输出 schema。
- 失败怎么办？→ 宽松 JSON 提取 → 重试一次 → 逐角色示例回退；主席失败按五人均分确定性回退。

**边界**
> 定位是"投稿前辅助自审"，不替代同行评审；报告里的分歧点目前是展示，不做自动仲裁。

### 4.3 文献研读（MCP + 多格式 + 三栏 + 3D 图谱）

**30 秒口语稿**
> 文献这块做了三件事。
> 第一，**接真实工具**。用 MCP 官方 SDK 起 Client 和 McpServer，走 `tools/list` 和 `tools/call`，真实打 arXiv 和 OpenAlex，工具只读、有参数 schema、超时 45 秒。
> 第二，**一份解析产物支撑三个场景**。PDF / Word / Markdown / CAJ 统一解析成 sections + figures + meta，阅读器、RAG 切片、引用图谱复用同一份结构。
> 第三，**三栏精读 + 3D 引用图谱**。左边原文、中间代码复现面板、右边对话，划词可翻译，引用关系用 3D 力导向图展示。

**可深挖**
- 为什么 MCP 会话是 request-scope？→ 一个请求一个 session，用完 close，避免长连接泄漏和多租户串号。
- CAJ 怎么解析？→ 先识别版本头，内部保留 PDF 文本流的做内联解析，否则启发式提取；失败会在元数据里标 placeholder，不假装解析成功。
- 3D 图谱数据哪来？→ 从解析出的 references 构建节点和边，前端渲染，不额外调模型。

**边界**
> CAJ 不是 100% 还原，复杂版式会降级；引用图谱的节点来自已解析文献，不是全网引用。

### 4.4 实验复现 + 图表生成

**30 秒口语稿**
> 复现做成五阶段流水线：代码解析 → 环境构建 → 数据准备 → 基线对齐 → 结果比对，每一步都有阶段日志，最后出一份和原文逐指标对照的可复现性报告。
> 实验侧做了参数看板和消融矩阵——给定变量自动生成笛卡尔积的实验组合；再对接 CCF 期刊库做匹配和截稿倒计时。
> 配图走 OpenAI 兼容的生图网关，按比例映射尺寸，失败降级矢量 SVG，不让任务中断。

**可深挖**
- 生图为什么中文要转英文？→ 模型中文渲染不稳定，会出现问号；所以中文说明强制转学术英文再出图。
- 生图超时怎么办？→ 180 秒超时，失败写 `render_warning` 并降级 SVG，任务继续。
- 消融矩阵怎么生成？→ 变量维度笛卡尔积 + 基线固定，输出可勾选的配置表。

**边界**
> 复现执行器目前是高保真编排，指标是建模数据；真实跑代码的 Docker/Wasm 沙箱在路线图上。
> 生图模型是通过 `IMAGE_MODEL` 配置的（代码默认 `gpt-image-2`），回答时说"图像生成网关（模型可切换）"最稳，不要说死某个模型版本。

### 4.5 RAG 检索

**30 秒口语稿**
> 我们的 RAG 有三个原则：**带页码、可降级、不编造**。
> 切片按章节走，步长 1000、窗口 1200，带 200 字重叠，每片携带章节标题和段落级页码；检索优先走向量余弦，topK=3、候选 12；Embedding 不可用自动降级词法检索，并把降级状态返回前端；可选 Rerank，但重排结果必须通过 ID 集合校验才采纳。
> 回答通过 reference 事件附文档 ID、页码、章节、原文片段和得分，用户能点回原文。

**可深挖**
- 为什么要 overlap？→ 避免关键句被切断；1000 步长 + 1200 窗口就是 200 字重叠。
- 页码怎么保证准？→ 解析阶段建立段落 → 页码映射，映射不到就 `page_verified=false`，宁可标"未验证"也不编。
- 为什么候选 12 只返回 3？→ 给 Rerank 留池子，同时控制上下文长度和成本。
- 怎么评测量化？→ 见第七节，这里是最容易被追问穿的地方，务必按口径回答。

**边界**
> 向量目前存进程内/JSON，生产目标是 pgvector；Rerank 是可选开关，默认关闭。

### 4.6 Harness 评测

## 五、高频问题与参考回答

> 编号 Q1-Q78，按面试官类型分组。每题控制在 3-6 行，现场够用；想更深就回到第三、四节展开。

### A. 动机与产品（Q1-Q6）

**Q1：为什么做这个项目？**
> 起因是我自己做科研时，一天里大量时间在工具之间搬东西，真正思考的时间被切得很碎。我判断这不是个人效率问题，是**工具形态问题**：通用模型有脑无手，垂直工具有手无脑，中间缺一层"能把专业能力串起来的编排层"。ScienceX 就是补这一层。

**Q2：和 ChatGPT、豆包、知网有什么区别？**
> 一句话：**它们回答问题，我们完成课题**。
> 通用助手交付"一次对话"，我们交付"一个课题"——上下文跨阶段流转并沉淀成资产；它们没有领域机制，我们有五角色盲审、消融矩阵、CAJ 解析、CCF 匹配、页码级溯源；而且我们模型中立，豆包这类模型可以通过网关接进来当底层引擎。我们卖的不是模型，是工作流和数据资产。

**Q3：用户是谁？谁付费？**
> 三层：硕博研究生是核心付费人群，论文是硬 KPI；课题组/实验室是团队版客户，导师是决策人；高校和院所是私有化客户。
> 定价四档：免费获客、19.9 学生价渗透、199 课题组版、机构定制。冷启动靠课题组内口碑扩散。

**Q4：你验证过需求吗？还是自嗨？**
> 老实说，验证是**定性为主**：我访谈了身边十几个研究生和两位导师，做了竞品矩阵，然后拿比赛现场当真实用户测试——评委和观众自己注册、自己点模块，我在旁边记录他们卡在哪。
> 定量验证还没做，这是我下一步要补的：埋点看全流程完成率和单篇精读耗时。对外材料里"调研耗时降 60%"我明确标注是目标估算，不是实测。

**Q5：为什么先做文献，不做写作？**
> 因为文献是科研的入口，也是最高频、最痛、最能建立信任的环节。写作环节用户已经习惯 Word + Grammarly，替换成本高；文献环节是"从 0 到 1"，而且天然带 RAG 和溯源的刚需——先把"可核查"这件事做成，后面所有模块都受益。

**Q6：商业化你怎么想？**
> 三条：学生价打穿决策门槛，课题组版做 B 端入口，私有化做毛利。成本端靠模型路由 + BYOK + 缓存。
> 但我不认为现在就该猛推商业化——先把"可信"做成口碑，科研用户对"编造"零容忍，信任比增长重要。

### B. 架构与选型（Q7-Q14）

**Q7：整体架构讲一下？**
> 六层：React SPA → Express 中间件链（CORS、Request-Id、限流、HMAC）→ 7 个业务路由域 → AI 能力层（灵犀引擎、记忆、RAG、MCP、模型网关）→ 模型网关 → 数据层。
> 三类数据流：同步 REST、流式 SSE、异步任务 + 独立进度流。接口统一 `/api/v1`，契约用 Zod 定义，OpenAPI 同源生成。

**Q8：简历写 FastAPI，代码里有吗？**
> 这里我要说清楚：**当前可运行版本是 Node.js + Express，FastAPI 是 AI 域的生产目标架构**，写在 TSD 里，我没有把 Python 版落地。
> 当时的判断是演示环境要"零依赖、秒级拉起、任何人 clone 就能跑"，Node 单进程最省事；生产上 AI 域独立成 FastAPI 更合理——算力调度、Python 生态、GPU 资源都在 Python 侧。
> 如果你希望简历更严谨，这条可以改成"Node.js + Express（生产规划 FastAPI）"。

> **提醒**：这是简历与仓库不一致的高风险点，建议面试前改简历或主动说明，不要等被问穿。

**Q9：为什么不用 NestJS / TypeScript 后端？**
> 两个原因：一是演示环境追求"零构建"，Node 直接跑，不用编译；二是这个项目的复杂度主要在 AI 编排，不在业务分层，Nest 的 DI 和模块系统收益不明显。
> 如果是生产团队协作，我会选 NestJS 或 Fastify——类型安全、插件生态、可测试性都更好，代价是启动和构建成本。

**Q10：为什么用 SSE 不用 WebSocket？**
> 因为需求是**单向流式**：服务端推 token，客户端只需要发一次请求。SSE 天然支持断线重连、走 HTTP 不用额外端口、Nginx 只要关掉 buffering 就行；WebSocket 要维护连接状态、心跳、多实例广播，成本高收益低。
> 需要双向实时协作（比如多人同时编辑）时再上 WebSocket。

**Q11：SSE 断线了怎么办？**
> 分两种：
> 对话流：前端 AbortController 中断，服务端监听 close 后 abort 上游请求，避免继续烧 token。
> 长任务：任务状态在服务端持久化，前端按任务 ID 重新订阅 `/tasks/:id/stream`，不依赖原连接。
> 还有个原则：**已经输出过 delta 的流，失败就失败，不重试、不补 done**，否则用户会看到重复内容或半截答案。

**Q12：长任务怎么做的？**
> 创建任务后立刻返回 task id，流水线在后台跑，每个阶段 `publishTaskEvent` 推进度；关键是**结果构建完成后才置 `done`**，防止前端收到 done 却拿不到结果。这是踩过坑之后改的。

**Q13：多实例部署，鉴权怎么办？**
> 用 HMAC-SHA256 无状态令牌：`sx1.<payload>.<signature>`，任何实例用同一个 master key 都能离线验签，不依赖共享 Session。多实例只要 `SCIENCEX_MASTER_KEY` 一致即可。
> 同时保留一个内存会话表做即时吊销——吊销是"尽力而为"，验签是"必须过"。

**Q14：为什么不用 JWT？**
> 本质上 HMAC 令牌就是"精简版 JWT"：三段结构、签名、过期时间都有。自己实现是为了零依赖、格式可控、payload 更小；JWT 的坑在于算法混淆（alg=none）和库漏洞，我们只允许 HS256 一种算法，反而更安全。
> 如果团队已经有成熟的 JWT 体系，我不会重复造轮子。

### C. Agent 编排（Q15-Q21）

**Q15：8 种模式具体区别？举一个 ReAct 的链路。**
> ReAct 一轮是：模型输出 thought（我要查什么）→ 发 `tool_call` → 执行工具 → 回 `tool_result` → 模型基于观察再想下一步。循环到给出答案或触达轮次上限。
> Plan-Execute 是先把任务拆成可编辑的计划卡（step 列表），用户能改，再逐步执行；CodeAct 是生成代码 → 沙箱执行 → 读结果 → 解读；Structured 是强制 JSON schema 输出，给下游组件用。

**Q16：Plan-Execute 和 ReAct 怎么选？**
> 任务步骤明确、需要用户干预的用 Plan-Execute，比如"帮我做一次复现"；步骤不确定、需要边查边想的用 ReAct，比如"这个领域最近有什么值得做的方向"。
> 我们的默认模式是 Plan-Execute，因为科研任务普遍步骤长、用户希望先看计划再执行。

**Q17：怎么防止 Agent 死循环、成本失控？**
> 四道闸：轮次上限、单次请求 deadline、按 userId 的滑动窗口限流（对话 30 次/分钟）、断连即 abort。
> 另外规划类调用用非流式 + 低温度 + max_tokens 限制，避免"想太久"。

**Q18：工具调用安全怎么保证？**
> 三个原则：**只读优先、来源可追溯、参数强校验**。
> 具体：MCP 只开放 `search_papers`，query 1-500 字符、limit 1-20，Zod 校验；超时 45 秒；写工具直接拒绝；CodeAct 的代码执行明确禁用真实系统调用。

**Q19：记忆怎么做的？会不会记错？**
> 三层：短期 RAM（当前会话）→ 滚动摘要（长对话压缩）→ 长期事实（跨会话沉淀）。
> 长期事实不是模型说记就记：先过 schema，再要求 `evidence` 必须在用户原话里能匹配到（`source.includes(evidence)`），importance < 0.5 丢弃，密钥/密码类内容直接过滤；写入时按 key/内容去重，超出容量按"重要性 × 新鲜度"淘汰。
> 所以它可能"记得不全"，但不容易"记错"。

**Q20：这 8 个模式是不是套壳？**
> 如果只是换 prompt，是套壳。区别在于**控制流不同**：ReAct 有循环和工具观察，Plan-Execute 有计划和逐步执行，CodeAct 有代码生成和执行结果回填，Structured 有 schema 约束和校验。控制流不同，失败模式就不同，容错策略也不同。
> 但我也承认：底层都是同一个模型，真正的差异化在编排和容错，不在"模式数量"。

**Q21：前端怎么渲染思考过程？**
> 统一订阅 SSE 事件：`plan` 渲染规划卡，`thought` 渲染思维链，`tool_call/tool_result` 渲染工具卡片，`delta` 追加正文，`reference` 渲染引用角标，`error` 渲染错误态。
> 因为事件协议统一，新增模式不需要改渲染层。

### D. 多智能体评审（Q22-Q27）

**Q22：为什么是 5 个角色？依据是什么？**
> 按"一篇论文能不能过"的真实攻击面拆的：理论上成不成立、方法新不新、实验证没证、写作清不清楚、伦理合不合规。这五个面覆盖了绝大多数拒稿理由，再加一个主席做合议，避免"五个专家各说各话"。

**Q23：怎么保证角色不串味？**
> 两层：system prompt 里明确"你只负责本维度，严禁越界评价其他维度"；输出 schema 只有 score / verdict / comments 三个字段，没有"总评"的位置，从结构上不给越界空间。

**Q24：5 个并发失败了怎么办？**
> 三级容错：
> 第一级，宽松 JSON 提取——去 Markdown 围栏、截取第一个 `{` 到最后一个 `}`、逐字段正则回补；
> 第二级，单角色重试一次，并把 max_tokens 从 1600 提到 2600（这是踩过的坑：推理 token 把 JSON 截断了）；
> 第三级，逐角色确定性示例回退，保证报告结构完整，任务不失败。
> 主席失败时按五人均分回退。核心原则：**局部失败不能拖垮整体**。

**Q25：主席会不会只是求平均分？**
> 不是。主席拿到的不是分数，是五份带评论的意见，要求它识别**分歧点**并给优先级。输出里除了总分，还有 P0/P1/P2 的修改清单——这个是平均分给不出来的。
> 当然，如果模型偷懒，确实可能退化成平均。我们用一个约束缓解：要求它"点名分歧与风险"，并在报告里保留五份原始意见，用户能自己判断。

**Q26：评审质量怎么证明？**
> 两层：结构层用自动化用例保证——报告必须含决策、六维评分、5 条角色意见，无密钥也要能返回；内容层目前靠人工抽检，我承认还没有和真实审稿意见做相关性分析。
> 下一步计划：拿 20 篇已有审稿意见的论文做对照，看"评审团提出的 P0 问题"和"真实审稿人提出的问题"重合度。

**Q27：和真实审稿人比呢？**
> 不能比。真实审稿人有领域直觉和责任，我们只是"投稿前的一面镜子"，帮作者提前看到明显漏洞。
> 产品里也写清了定位：辅助自审，最终决策权在作者。

### E. RAG（Q28-Q36）

**Q28：RAG 全链路讲一下。**
> 入库：解析 → 章节化 → 切片（带页码）→ Embedding（批 32）→ 校验向量 → 存索引。
> 检索：query 向量化 → 余弦召回候选 12 → （可选）Rerank 重排 → 取 topK=3。
> 生成：把片段拼进 prompt，约束"只基于片段回答"。
> 回传：`reference` 事件带 doc_id / page / section / snippet / score。
> 降级：Embedding 不可用 → 词法检索，返回 `mode=keyword-fallback` + `degraded=true`。

**Q29：为什么是 1000 和 1200 这两个数字？**
> 1000 是步长，1200 是窗口，差值 200 就是重叠区。这样一句话即使跨在边界上，也会完整出现在至少一个切片里。
> 为什么不更大？切片越大，召回越不精准、上下文越贵；越小，语义越碎。1000 字大概是一到两个自然段，对论文来说是合适的语义粒度。

**Q30：为什么 topK=3、候选 12？**
> 3 是给模型的上下文预算——再多会稀释重点、增加成本；12 是给 Rerank 留的重排池，经验值是最终结果的 4 倍。
> 这两个都是可配的，不是写死的。

**Q31：Embedding 服务挂了怎么办？**
> 自动降级词法检索：按中英文分词，算词命中率排序。同时把 `mode` 和 `warning` 返回给前端，用户能看到"现在是降级模式"。
> 我们的原则是**降级可以，静默不行**。

**Q32：Rerank 为什么要做 ID 校验？**
> 因为模型会"幻觉 ID"。如果它返回一个不存在的片段 ID，直接采纳会导致引用错乱。所以我们校验三件事：必须是数组、ID 不能重复、每个 ID 必须在候选集合里；任一不满足就丢弃重排结果，保留原顺序。

**Q33：页码怎么保证准？**
> 解析阶段就建立"段落 → 页码"映射，切片继承；映射不到时 `page_verified=false`，前端显示"页码未验证"。
> 宁可标不确定，也不给一个看起来很像的错页码——这在学术场景是红线。

**Q34：怎么防止幻觉？**
> 四层：检索约束（只基于片段）、空检索明确说"无可用片段"、引用必须挂真实片段、评测里 4 条"拒答诚实度"强制命中。
> 但我不说"消灭幻觉"，我说"可核查"——用户能点回原文验证，这比承诺不编造更可靠。

**Q35：简历写 Top-3 从 76% 提升到 93%，怎么测的？**
> 这是本场面试**最高风险**的问题，回答前先看第七节 7.2。三种口径按你手里的证据选：
> **有评测产物**：说清样本量、标注方式、指标定义、对比组（词法 vs 向量 vs 向量+Rerank），并主动说"这是内部小样本，不是公开 benchmark"。
> **没有产物**：不要硬编。说"这个数字是我在内部小样本上的离线评测，样本和方法我需要回去核对一下原始记录，我不想给你一个不可核查的数"，然后把话题转到可验证的工程指标（页码溯源、空检索不编造）。
> **最稳的做法**：面试前把这条改成"自建 320 条查询的离线评测，Top-3 命中从 X 提升到 Y（内部口径）"，或者直接删掉数字，只讲机制。

**Q36：为什么不用 LangChain / LlamaIndex / 现成向量库？**
> 三个原因：一是演示环境要零依赖可复现，多一个框架多一层版本坑；二是 RAG 的核心逻辑（切片、召回、降级、校验）只有两百行，自己写反而可控；三是我想把"降级"和"引用校验"做成自己的语义，框架里这些是黑盒。
> 生产上我会用 pgvector 或 Milvus，编排层可以考虑 LangGraph，但前提是团队需要。

### F. MCP 与工具安全（Q37-Q41）

**Q37：MCP 是什么？为什么用它？**
> MCP 是模型上下文协议，本质是**把工具接入标准化**：工具方实现 server，应用方实现 client，通过 `tools/list` 发现能力、`tools/call` 调用。
> 用它是因为"模型中立 + 工具开放"——今天接 arXiv，明天接校内数据库，只要实现同一个协议，Agent 侧不用改代码。

**Q38：握手过程讲一下。**
> 起一个 McpServer 注册工具（名称、描述、Zod inputSchema），再起 Client，用 InMemoryTransport 建一对连接，`connect` 完成握手；然后 `listTools` 枚举能力，`callTool` 调用。整个会话限定在一个请求内，`finally` 里 close 掉 client 和 server。

**Q39：为什么是 request-scope，不是长连接？**
> 三个考虑：资源——长连接在多租户下容易泄漏；隔离——不同用户的会话不能串；简单——无状态更容易水平扩展。
> 代价是每次调用要重新握手，有几十毫秒开销；对检索这种低频调用可以接受。

**Q40：为什么只读？写工具怎么办？**
> 科研场景里"写"意味着改数据、发请求、跑代码，风险高。所以第一版只开放只读检索，写操作明确拒绝。
> 如果要做写工具，至少要：用户显式确认、操作审计、幂等设计、沙箱隔离、可回滚。

**Q41：MCP 和 Function Calling 什么区别？**
> Function Calling 是"模型输出一个调用意图"，工具怎么接、怎么发现、怎么鉴权，各家自己定；MCP 是**协议层标准**，解决的是工具的可移植性和发现机制。
> 可以理解为：Function Calling 是动词，MCP 是插头标准。

### G. 评测与质量门禁（Q42-Q46）

**Q42：12 条用例怎么设计的？**
> 按"学术严谨性"拆的：方法类（消融、随机种子、显著性）、文献类（综述组织、跨源去重）、写作类（润色边界、术语一致）、选题类（创新性与可行性），再加 4 条诚实性红线（引用、数据、页码、无据结论）。
> 每条给定"必须出现的要点"，用正则命中率打分，逐题设最低分数线。

**Q43：正则命中率能代表质量吗？**
> 不能，脚本里我自己写了"命中率不等价于事实正确性"。它拦的是**硬错误**：该拒答却编了、该提基线却没提。
> 它的价值是"防回退"，不是"证明强"。要评质量得上 LLM-as-judge + 人工抽检，那是下一步。

**Q44：为什么 4 条必须等于 1？**
> 因为这 4 条不是能力项，是合规项。引用找不到、数据没有、页码不确定、结论无据——这四种情况只要编一次，产品在学术场景就失去信任。所以设成 1，不给"平均分"留余地。

**Q45：CI 怎么卡的？**
> GitHub Actions 五步：后端 55 条测试 → 覆盖率卡口（lines 55 / functions 50 / branches 60）→ AI 质量回归 `eval/run.js --check` → 前端 typecheck + lint → build。任一步失败就红。
> 有个细节要说清楚：CI 里跑的是**离线模板分**（不调外部模型），真实模型对比要显式加 `--live` 并配密钥；55 条里也有 3 条真实模型用例无密钥时自动跳过。这些我都写在 README 里，不假装 CI 验证了模型质量。

**Q46：线上怎么监控质量？**
> 目前只有用量和错误率，还没有质量监控，这是缺口。
> 我计划做三件事：抽样人工评审、把 `reference` 点击率作为"可核查性"代理指标、把降级率（`degraded=true` 占比）做成告警——降级率突然升高说明 Embedding 服务有问题。

### H. 工程、安全与部署（Q47-Q55）

**Q47：限流怎么做的？为什么按 userId？**
> `rate-limiter-flexible` 滑动窗口，对话 30 次/分、写作和文献 60 次/分，按 scope 分桶，桶 key 优先用令牌里的 userId，取不到才用 IP。
> 按 userId 是因为实验室、学校常常共享出口 IP，按 IP 会误伤；超限返回 429 + `Retry-After`。

**Q48：SSRF 怎么防？**
> 模型网关允许用户填自定义 baseUrl，这是 SSRF 高危面。我们只放行公网域名，拦截 127.0.0.1、内网段、链路本地、环状地址，并且校验解析后的 IP，不只看字符串。
> 测试里专门有一条：公网放行、内网抛异常。

**Q49：批量赋值怎么防？**
> 请求体走 Zod schema 白名单，未声明字段直接剔除；比如更新资料时夹带 `plan` 想升级套餐，会被丢掉。测试里有一条专门验证 `id` 不变、`plan` 未提升。

**Q50：上传伪装怎么防？**
> 内容嗅探：不只看扩展名，检查文件头。`.js` 内容改名 `.md` 会被拦。另外限制 72MB、只允许四种格式。

**Q51：并发写 JSON 怎么保证不损坏？**
> 单文件 Store 用**串行写队列**：所有 persist 进同一个队列按序执行，写临时文件再原子 rename；序列化失败直接 reject，不污染队列；单次失败不阻塞后续。
> 测试里用真实磁盘并发写验证"文件始终是完整合法 JSON"。

**Q52：覆盖率 55% 是不是偏低？**
> 是偏低，但这是"卡口"不是"目标"。定 55/50/60 是因为当前实测略高于它，卡口略低于实测才能"防回退又不误伤"。
> 更重要的是覆盖的内容：权限隔离、SSRF、批量赋值、伪装上传、并发写、流截断——这些是高风险路径，比追求行数有意义。

**Q53：日志怎么追踪？**
> pino 结构化日志 + AsyncLocalStorage，入口生成 `X-Request-Id`，全链路透传，响应头回传同一个 id；日志里带耗时和状态分类，排查时一个 id 串起来。
> 敏感字段不落日志。

**Q54：无密钥回退，算不算"造假"？**
> 不算，前提是**标注**。配置密钥时走真实模型；没有密钥时回退模板，并且响应里带 `mode`、界面上明确标"演示模板"。我们所有材料都区分"真实调用"和"确定性回退"。
> 真正的问题是"不标注"，那才是造假。

**Q55：部署怎么做的？**
> 两条路径：Vercel 双 service（前端 Vite 构建 + 后端 Express，`/api/*` rewrite），以及 Docker + Nginx 自托管。SSE 在 Nginx 要关 `proxy_buffering`、`Connection ''`、读超时 300 秒。
> 多实例必须配同一个 `SCIENCEX_MASTER_KEY`，否则令牌验不过。

### I. 前端与性能（Q56-Q60）

**Q56：SSE 前端怎么解析？跨块 UTF-8 怎么办？**
> Fetch 拿 ReadableStream，手写解码器按 `\n\n` 切事件、按 `data:` 取载荷；跨块的多字节字符用 `TextDecoder({stream:true})` 处理，保证中文不被截断。
> 每条流有独立 streamKey，避免多路流互相覆盖。

**Q57：3D 引用图谱怎么做的？性能怎么样？**
> 自研 SVG/CSS 3D 力导向，节点是文献、边是引用关系，支持旋转和聚焦。没有引入 three.js，是为了控制包体积。
> 节点多的时候会降级成 2D 或只渲染一跳邻居——这一点我承认做得比较轻，是展示性功能。

**Q58：长列表怎么优化？**
> 虚拟滚动（VirtualList），只渲染可视区 + 缓冲区；配合分页和骨架屏。

**Q59：移动端怎么适配？**
> `useIsMobile` 探视口 + CSS 响应式，九大界面 ≤768px 单列堆叠，部分卡片用 scroll-snap 横向滑动、CSS order 重排。移动端定位是"轻消费"——看进度、审报告，不做重活。

**Q60：状态管理为什么不用 Redux？**
> 只有两块全局状态：认证和当前课题组。自研两个轻量 store（Context + useReducer）就够了，Redux 的样板代码和包体积不划算。
> 如果状态复杂度上来，我会选 Zustand，而不是 Redux。

### J. 数据层与演进（Q61-Q64）

**Q61：JSON Store 能上线吗？**
> 演示可以，生产不行。它没有事务、没有并发控制、不支持水平扩展，单机几千用户就会成为瓶颈。
> 我在 README 里明确写了这是"演示级持久化"，生产目标是 PostgreSQL + Redis + pgvector，接口契约已经按多租户设计好，迁移时业务代码不用大改。

**Q62：如果重做一次，你会怎么改？**
> 三件事：
> 第一，数据层一开始就上 PostgreSQL，哪怕是本地 Docker，也不要留"以后再说"的债；
> 第二，把 AI 质量评测从"正则命中"升级成"断言集 + LLM judge + 人工抽检"三层；
> 第三，把工具执行做成真沙箱（Docker/Wasm），因为 CodeAct 的价值全在"真跑"。

**Q63：向量库怎么选？**
> 单机/中小规模选 pgvector——和业务库同源，事务和备份都好办；千万级以上或需要多路召回选 Milvus；纯演示可以用内存 + JSON。
> 我们现在的量级，pgvector 足够。

**Q64：成本怎么控？**
> 四招：模型路由（简单任务走小模型）、BYOK（用户自带密钥）、上下文裁剪（topK=3 而不是 10）、缓存（相同 query 命中缓存）。
> 另外规划类调用用非流式 + 低 max_tokens，避免"想太久"。

## 六、四个高光故事（STAR，背下来）

> 面试官判断"真做过"的唯一方式是听你说**失败**。下面的故事都有一个共同结构：现象 → 根因 → 修法 → 可复用的经验。每个讲 60-90 秒。

### 6.1 流已经输出一半，绝不能补一个 done

- **S**：联调时发现，上游网关在流中途超时。早期实现会把它当成"正常结束"补一个 `done`，用户拿到半截答案却显示已完成；如果按普通 HTTP 逻辑重试，又会把已经输出的内容再吐一遍。
- **T**：让"失败"对用户是确定的、不重复的。
- **A**：在流适配器里记录 `sentDelta` 标记——一旦向客户端发过 delta，就禁止重试；只发 `error` 事件并标记 `retryable=false`；绝不伪造 `done`。同时把这条写进测试："流已输出后截断不得伪造 done"。
- **R**：用户不会再拿到"半截却显示完成"的答案；这条用例至今在 CI 里守着。
- **可复用经验**：**流式系统的难点不在正常路径，在失败语义。** 幂等和"已产生副作用不可重试"是同一类问题。

### 6.2 五个 Agent 并行，最后死在 JSON 上

- **S**：评审团第一次联调，五个角色里总有一两个解析失败，报告缺角色。
- **T**：让报告结构永远完整。
- **A**：查日志发现两个原因——模型把 JSON 包在 Markdown 围栏里；推理 token 把 JSON 截断（max_tokens 给少了）。三层修：宽松提取（去围栏、截取首尾大括号、逐字段正则回补）→ 单角色重试一次并把 max_tokens 从 1600 提到 2600 → 仍失败则用该角色的示例意见确定性回退，并标记 `mode=fallback`。
- **R**：无密钥、断网、模型抽风，报告都能出；主席失败时按五人均分回退。
- **可复用经验**：**调用外部模型要像调外部 HTTP 一样设计**——超时、重试、降级、可观测，一个都不能少。

### 6.3 在只读文件系统上，程序不能崩

- **S**：部署到 Vercel 后，写数据报 `EROFS`，进程直接退出。
- **T**：本地、Docker、Serverless 三种环境都要能跑。
- **A**：启动时探测数据目录可写性，可写落项目 `.data`，不可写回退系统临时目录；写盘失败只告警不炸进程；端口被占用则自动 +1 并写入 `.port`，Vite 读这个文件配代理。
- **R**：克隆即跑，多人同机不冲突，Serverless 不崩。
- **可复用经验**：**"能跑"和"到处能跑"是两件事**，环境假设要显式化。

### 6.4 404 不是"没数据"，是"你请求的东西不存在"

- **S**：新注册用户进工作台，首屏一片空白，弹"项目不存在"。
- **T**：让新用户零数据也能正常进入。
- **A**：首屏是并发请求，其中一个带 `project_id` 的接口返回 404，导致整批 Promise 失败。根因是我把"显式指定了无权限的 project_id"和"新用户还没有课题"当成同一种情况。改为：显式指定且无权限 → 404；未指定且无课题 → 返回空看板 `project: null`。
- **R**：新用户首屏不再中断，权限语义也更准确。
- **可复用经验**：**HTTP 语义要精确**，把"空集合"和"不存在"混用，故障会以最意想不到的方式扩散。

## 七、数字口径与风险预案

> 这一节决定你会不会被追问穿。原则：**能被命令复现的放心讲，只有文档没有产物的谨慎讲，说不清来源的不要讲。**

### 7.1 三档数字表

| 档位 | 数字 | 现场怎么用 |
| :--- | :--- | :--- |
| **A. 可复现（放心讲）** | 55 条自动化用例 / 5 个测试套件；覆盖率卡口 lines 55%、functions 50%、branches 60%；12 条 AI 评测、4 条强制命中=1；约 70 个端点；6 个内置模型；5 个内置技能；2 个真实 MCP 工具（arXiv / OpenAlex）；限流 30 / 60 次每分钟；令牌 7 / 30 天；上传 72MB；4 种文档格式；后端约 5.2k 行、前端约 16.6k 行 | "这些数字您 clone 下来跑 `npm test`、`npm run coverage`、`npm run eval:ai` 就能复现。" |
| **B. 需谨慎（仓库无产物）** | RAG Top-3 76%→93%；Recall@5 0.71→0.92；MRR 0.66→0.85；320 条人工标注集；生图 60-70 秒（单次实测） | 只在能说清"样本量 + 标注方式 + 指标定义"时讲，并主动声明"内部小样本，不是公开 benchmark" |
| **C. 不要主动讲** | 具体 DAU / 付费用户数 / 收入 / 真实用户调研样本量 | 被问到就说"还没有规模化数据，我不编这个数" |

### 7.2 三个高风险点的处理方案

#### 风险 1：RAG 的 76%→93%、Recall@5 0.92、MRR 0.85、320 条标注集

**现状**：仓库里只有 `backend/eval/cases.json`（12 条学术质量用例，正则命中），**没有 RAG 检索评测脚本，也没有 320 条标注集**。也就是说这四个数字目前无法在现场复现。

**方案 A（推荐，一次性解决）**：补一个 RAG 评测脚本 + 标注集，让数字变成可复现的。
- 标注：320 条 query，每条标 1-3 个相关 chunk（doc_id + chunk_id）。
- 三组对比：纯词法 / 纯向量 / 向量 + Rerank。
- 指标：Top-3 命中率、Recall@5、MRR，输出 JSON 报告；`--check` 接进 CI。
- 这样回答就变成："我写了个 `eval/rag.js`，320 条查询、三组对比，Top-3 是 X→Y，您可以直接 `npm run eval:rag` 复现。"

**方案 B（保守口径）**：
> "这个 93% 是我在内部小样本上做的离线评测，指标定义是 Top-3 里是否命中人工标注的相关片段。它不是公开 benchmark，样本量也不大，所以我在简历里给的是区间而不是精确小数。我更愿意讲机制：切片带重叠、向量失败降级词法、Rerank 强制校验 ID。"

**方案 C（最稳）**：面试前改简历，把这条改成可核查的表述：
> "自建 320 条查询的离线检索评测，覆盖词法 / 向量 / 向量+重排三组配置，输出 Top-3、Recall@5、MRR 报告并接入 CI。"
> （不写具体数值，把话题引到"我怎么测"而不是"你测出多少"。）

**被追问时的万能兜底**：
> "这个数我现在没法现场证明，我不想给您一个不可核查的数。我能现场证明的是：页码级溯源、检索为空不编造、无效向量拒绝入库——这三条都在测试里。"

#### 风险 2：简历写 FastAPI

**现状**：仓库是 Node.js + Express，`docs/TSD.md` 里 FastAPI 属于**生产目标架构**，没有落地代码。

**处理**：面试前把简历改成 "Node.js + Express（AI 域生产规划 FastAPI）"，或直接删掉 FastAPI。若已被问到，用 Q8 的回答：承认未落地 + 说清当时取舍 + 说清生产上为什么合理。

#### 风险 3：简历写 image2.5

**现状**：`backend/src/ai/image.js` 默认模型是 `gpt-image-2`，通过 `IMAGE_MODEL` 环境变量可切换，走 OpenAI 兼容 `/v1/images/generations`。

**处理**：回答时说"**图像生成网关，模型可配置**"，不要咬死版本号。若面试官追问版本，如实说"线上配置的是哪个版本以环境变量为准，代码默认 gpt-image-2"。

#### 附带提醒："越权返回 404"

代码里资源越权（会话 / 项目 / 技能 / MCP / 记忆）统一走 `notFound` 返回 404；**模型无权限是显式失败关闭**（`enabled=false`），不是 404。回答时说"越权资源统一 404，模型无权显式失败关闭"，不要说"所有越权都是 404"。

### 7.3 被质疑"数据是不是编的"时的三段式

1. **承认边界**："演示数据是建模数据，我在 README 里标了 `source=demo`，测试里也验证了不冒充真实数据。"
2. **给出可验证项**："但架构、鉴权、限流、解析、RAG 降级、MCP 握手、评测门禁都是真实实现，您可以直接跑。"
3. **回到价值**："我认为演示项目最重要的不是假装生产级，而是**边界清楚、可复现、可演进**。"

## 八、反问环节：问什么显得专业

按面试轮次选 2-3 个，不要一次问完。

1. **"你们现在的 AI 功能，失败率大概是多少？降级策略是谁定的？"**
   为什么好：直接切到你的强项（容错设计），同时试探团队成熟度。
2. **"这个岗位前三个月最希望我解决的一个问题是什么？"**
   为什么好：把话题从"评估你"转成"一起解决问题"。
3. **"你们做 AI 质量评测吗？是用人工抽检还是 LLM-as-judge？"**
   为什么好：显示你有评测意识，不是只会调 API。
4. **"团队现在的数据层是什么？向量检索是自建还是用云服务？"**
   为什么好：显示你关心生产落地，也为 Q61-Q63 做铺垫。
5. **"您觉得我在这个项目里，最需要补的一块是什么？"**
   为什么好：收尾时把评价权交回去，显得开放；对方的回答还能帮你判断后续怎么聊。

**不要问**：加班多不多、转正率多少、能不能远程（这些留给 HR 轮，且容易减分）。

## 十、面试前 10 分钟速查卡

**五句话**
1. 一站式科研 AI 工作台，把"搬数据"交给 Agent。
2. 三个抓手：SSE 全链路、多智能体容错、可核查 RAG。
3. 最重要的事：把不确定变成可见（降级、回退、标注）。
4. 工程差异化：55 条用例 + 12 条评测接进 CI。
5. 价值：可复现、可追溯、可问责。

**三个深挖点（每个 40 秒）**
- 流式：7 类事件 + 断流不伪造 done + 断连 abort 上游。
- 评审团：5 角色隔离 + 并行 + JSON 三级容错 + 主席合议。
- RAG：1000/1200 重叠切片 + 向量/词法降级 + Rerank ID 校验 + reference 溯源。

**五个数字**
- 55 条用例、12 条评测、4 条强制命中=1、限流 30/60、覆盖率 55/50/60。

**三条边界（主动说）**
- JSON Store 是演示级，生产要 PostgreSQL + pgvector。

- Vision / ASR 是目标态，未交付。

**两个反问**
- 你们 AI 功能的失败率和降级策略是谁定的？
- 前三个月最希望我解决什么问题？

**最后一句话（收尾用）**
> 这个项目可能不是一个完美的产品，但它是我认真做过的一个工程：我知道它哪里能跑、哪里会挂、哪里是演示。如果您给我一个生产环境，我知道第一步该换什么。
