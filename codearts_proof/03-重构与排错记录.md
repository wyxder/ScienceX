## 二、案例 A：订阅订单「正在创建收银台」卡死

**提交**：`f2ba253 fix: 修复订阅订单收银台卡死与支付宝支付回跳核销异常` ｜ **文件**：`frontend/src/pages/Account.tsx`、`frontend/src/pages/landing/LandingPricing.tsx`、`backend/src/routes/payment.js`

### 现象

点击订阅套餐后，界面长期停留在「正在创建收银台…」，既没有跳转，也没有失败提示；用户只能刷新页面。

### 根因

1. **浏览器弹窗拦截**：收银台窗口在 `await` 请求返回后才 `window.open`，此时已脱离用户点击的同步上下文，被浏览器判定为脚本弹窗而拦截；
2. **缺少失败分支**：接口异常或超时后前端没有终态提示，`payLoading` 一直为 true；
3. **回跳核销不可靠**：同步回跳页直接信任 URL 参数，未以订单查询结果为准，可能出现"支付成功但权益未开通"或反过来的误判。

### 方案

1. 点击的**同步阶段**先打开收银台窗口（`openCashierWindow()`），接口返回后再把支付表单写入该窗口；
2. 请求增加 25 秒超时与可读错误提示（"创建收银台超时，请检查网络后重试"）；
3. 回跳页按订单号查询真实状态后再核销，统一兜底到 `/#/account?tab=billing&pay_result=...`；
4. 首页与账户页两个入口采用同一套逻辑，避免行为分叉。

### 验证

- 异常路径：接口不返回时 25 秒内出现错误提示，窗口被关闭；
- 正常路径：收银台正常打开，支付完成后回跳核销；
- 回归：`npm test` 全绿；支付相关接口契约不变。

### 口述版（30 秒）

> 收银台卡死不是支付接口慢，而是窗口打开时机错了：异步返回后再开窗会被浏览器拦截。修法是把开窗挪到点击的同步阶段，再补超时与失败提示；回跳核销改为以订单查询结果为准，避免"付了钱没开通"。

## 三、案例 B：PDF 解析参数超长导致精读失败

**提交**：`60dac48 fix: 文献 Agent 改为基于文档全文回答并修复 PDF 解析参数超长失败` ｜ **文件**：`routes/documents.js`、`lib/parser.js`、`lib/rag.js`、`ReaderAgentPanel.tsx`

### 现象

上传较大的 PDF 后，精读/问答失败；日志提示参数超长。

### 根因

1. 整篇全文一次性传入子进程或模型请求，超出命令行参数长度与上下文窗口限制；
2. 文献 Agent 只基于检索片段回答，长文档中跨章节的问题容易召回不足。

### 方案

1. 解析改为**分段处理**，按章节/页码切片（1000 字窗口、单片上限 1200 字），携带章节标题与页码；
2. 文献 Agent 改为**基于已解析全文**回答，检索片段用于定位与引用，不再把全文塞进单次参数；
3. 保留页码溯源与 `page_verified` 标记，检索为空时明确告知"无可用片段"，不编造。

### 验证

- 文档上传 → 结构化 → 单篇问答链路用例通过；
- RAG 页码溯源、无效向量拒绝入库、检索为空不编造等用例通过；
- 前端精读面板正常渲染引用片段。

## 五、排错方法（可复用）

| 步骤 | 动作 | 本项目的例子 |
| :---: | :--- | :--- |
| 1 | 先看**终态**与**日志**，不猜业务 | 支付卡死先看前端状态机与 `payLoading`；PDF 失败先看参数长度报错 |
| 2 | 缩小到**最小复现** | 单套件 `ai-services.test.js` 0.7 秒跑完，先快速失败 |
| 3 | 区分**架构问题**与**实现问题** | 登录态随机失效是"内存当全局存储"的架构假设错误，不是 token 算错 |
| 4 | 优先**降级**而非硬崩 | 生产缺配置改为 warn + 能力降级，`/health` 不再陪葬 |
| 5 | 修复必须带**回归证据** | 每次修复后跑全量 74 条 + 前端 typecheck/build |
| 6 | 把结论写进**文档** | `解决.md` 沉淀 10 个问题的现象→根因→方案→结果 |
